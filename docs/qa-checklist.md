**결과 읽는 법:** 아래 “통과 (직접 호출)”는 실제 제출 소스의 Java 메서드를 호출해 응답·명단·정원을 검증한 결과입니다. Spring 서버의 요청 바인딩, Content-Type, JavaScript, 화면 표시, Network 확인까지 통과했다는 뜻은 아닙니다. null 인자를 통한 누락 검증도 HTTP에서 키를 누락한 검증과 구분합니다. H02 직접 호출은 기본 이름을 전달한 것이며, 기본값 바인딩은 별도로 HTTP `/greet`로 확인했습니다.

검증 대상: `submission/greeting-api/src/main/java/com/example/sesac_spring_boot_study/`의 컨트롤러·서비스. 검증 과정에서 제품 코드는 수정하지 않았습니다. 실패 및 동일 정원 요청에서는 요청 전후 명단 문자열과 정원을 비교했습니다. 승격 시 기존 id 유지와 신청 순서, 취소 후 재신청도 확인했습니다.

### 확인된 문제 소지와 남은 확인

- **동시 요청 미검증:** 서비스의 공유 Map과 id 변경이 동기화돼 있지 않습니다. 여러 요청이 동시에 들어오면 중복 검사·정원 검사·id 발급의 경쟁 가능성이 있습니다. 이번 순차 QA에서 재현된 실패는 아닙니다.
- **오류 안내 구체성:** 없는 id·이미 취소한 id는 현재 `올바르지 않은 입력입니다`로 안내합니다. 상태 유지는 통과했지만, 사용자에게 이유를 더 명확히 알리려면 `해당 id의 참가자가 없습니다`로 보완할 여지가 있습니다.
- **화면·Network 증거 필요:** 아래 직접 실행 결과만으로 수업의 “화면에서 수행·Network 확인” 요구사항이 완료되지는 않습니다.

## 사용자가 진행할 순서

1. 제출할 프로젝트 `submission/greeting-api`를 IDE에서 열고 실행합니다. 다른 코드로 실행 중인 8080 서버가 있다면 해당 서버를 종료하고 제출 코드로 실행하세요.
2. 서버 재시작으로 빈 명단·정원 3을 준비합니다. 재시작은 기존 메모리 명단을 초기화하므로 필요한 기록은 먼저 보관하세요.
3. `/study.html`을 열고 F12 → Network → Fetch/XHR를 선택합니다. Network 기록을 지우고 시작하면 요청을 찾기 쉽습니다.
4. H01~H03을 확인한 다음, **A01~A10 → B01~B11 → C01~C15 순서**로 실행합니다. 각 행의 실제 결과를 본인의 화면·HTTP 응답으로 갱신하고 통과 여부에 `화면·Network 확인`을 표시하세요.
5. 신청마다 반환된 id를 아래 표에 기록합니다. B09에서는 A의 최초 id, B10에서도 같은 최초 id를 사용합니다. B11 재신청 id는 따로 기록합니다.
6. 모든 실패 요청에서 직전 명단과 직후 명단을 비교합니다. 정원 실패 응답의 현재 정원도 확인합니다. 성공·실패 응답은 화면 또는 Network의 Response에서 복사해 기록합니다.
7. A~C 실행 중 N01~N08을 함께 확인합니다. Content-Type은 Headers, 입력 키는 Payload, 문자열 응답은 Response에서 봅니다.
8. C15까지 마친 뒤 서버를 재시작하고 D01~D04를 실행합니다. D02의 X·Y id도 실제 응답을 사용하세요.
9. 마지막으로 서버를 종료한 뒤 명단 새로고침을 눌러 N09 연결 오류 안내를 확인합니다. 이후 필요하면 서버를 다시 실행합니다.
10. 실패가 있으면 맨 아래 수정·재실행 표에 기록하고, 수정 후 사전 조건부터 다시 맞춰 같은 항목을 재실행합니다.
11. 실제 실행 환경·결과·남은 문제를 README에 반영합니다. 체크리스트가 저장소 밖에 있다면 제출 저장소의 `docs/`에도 포함한 뒤 커밋합니다.
